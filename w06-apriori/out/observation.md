# 6주차 · 관찰 기록

## Task 1 — A-Priori와 연관 규칙
support 50에서 1468 → 0은 confidence 0.839, 반대 0 → 1468은 0.004인데, 둘 다 같이 나온 장바구니 52개를 세지만 기준 집단이 1468을 산 62개냐 0을 산 13,080개(65.4%)냐가 달라서이고, 쓸모 있는 주장은 1468 → 0 쪽이다.
confidence 1위 규칙 1468 → 0은 lift가 1.28로 거의 1배라 안 믿는다(0을 사는 원래 비율 0.654와 비슷한 수준). 대신 lift 1위는 252 ↔ 270(15.1배, 같이 나온 장바구니 73개)으로 생성기가 심어 둔 쌍이었다.
brute force는 C(2000,2) = 1,999,000개 카운터가 필요하고, A-Priori는 pass 1에서 1,849개 항목만 남아 삼각 배열이면 1,708,476개, 실제로 같이 나온 쌍만 세면 820,259개였다.

## Task 2 — support를 낮추면
Apple M4(10코어), 16 GB, 7주차 측정이 같이 돌던 상태(load average 7~9)에서 support를 400 → 1까지 내렸는데 견디기 어려운 지점은 안 왔고(support 1도 3.5초, 최대 RSS 590 MB), 먼저 바닥난 건 pass 1의 거르는 힘이었다(support 25부터 2,000개 항목이 전부 통과해 카운터가 893,456개에서 멈춤).
카운터는 support를 반으로 줄일 때마다 5.54 → 4.67 → 3.00배(400 → 50)로 두 배보다 빠르게 늘었는데, 통과 항목이 약 2.4배씩 늘고 쌍 수는 항목 수의 제곱에 비례하기 때문이다.
답(빈발 쌍)은 약 2.9~3.1배씩만 늘어서 답 하나에 드는 카운터가 42.5개(support 400) → 128개(50)가 됐고, 그래서 "threshold를 조금만 낮추자"는 답 수만 보면 싸 보여도 실제 비용은 훨씬 크다.

## Task 3 — pass 2를 줄이기 (PCY)
bucket은 2^20 = 1,048,576개로, pass 1에서 해시한 쌍 3,427,037번을 나누면 bucket당 평균 3.3개라 support 50보다 훨씬 작아 대부분 걸러지게 골랐고, peak 카운터가 820,259 → 13,191개(98.4%, strong)로 줄었다(빈발 쌍 6,397개 동일, 시간 1.00 → 1.62초).
솔직하게 세면 pass 1의 bucket 정수 1,048,576개가 baseline 카운터 820,259개보다 많아 정수로는 아낀 게 아니라 옮긴 것이고(바이트로는 8.4 MB 배열 vs Python 카운터 107.7 MB라 peak 8.9 MB), bucket 수는 고정이고 쌍 수는 데이터와 함께 늘어서 baseline이 셀 쌍 수가 bucket 수를 넘을 때부터 이긴다(이 데이터는 2^18개면 262,144 + 38,782 = 300,926으로 이미 이김, 단 쌍 출현 수 ÷ bucket 수 < support여야 필터가 작동).
bucket을 2^16개로 줄이면 bucket당 평균 52.3개로 support를 넘어 카운터가 317,519개, 2^14개는 819,951개, 2^12개는 820,259개로 baseline과 같아져 필터가 아무 일도 안 했지만, 진짜 빈발 쌍이 든 bucket은 반드시 기준을 넘으므로 빈발 쌍은 모든 크기에서 같았다.
