# 3주차 · 관찰 기록

## Task 1 — 민해시와 LSH

행(조각 번호)을 위에서 아래로 한 번만 훑으면서 그 조각을 가진 문서의 signature 칸만 고치면, 데이터를 한 번 읽고 버려서 메모리에 안 들어가는 큰 행렬도 처리할 수 있다. 문서(열)마다 따로 훑으면 문서 수만큼 데이터를 다시 읽어야 한다.

hash 개수가 band 수로 안 나눠떨어지면 나머지 행을 앞쪽 band에 하나씩 나눠서 band 길이 차이를 최대 1로 했다. 한 band에 몰아주면 그 band만 길어져서 두 signature가 일치하는 경우가 급격히 준다.

S1–S4 추정이 1.0인데 진짜는 2/3인 건 hash가 2개뿐이라서고, 줄이려면 hash 함수를 늘려야 한다. 대신 조각마다 hash 계산이 늘어 시간이 더 걸리고, 문서마다 signature가 길어져서 저장도 늘어난다.

## Task 2 — 교차점

교차점은 n=800~900 사이다(800: brute 1.07초 / LSH 1.13초, 900: brute 1.37초 / LSH 1.26초). 기계는 Apple M4(10코어), 16 GB RAM이다. LSH는 비교 전에 minhash로 signature를 만드는 준비 작업이 항상 필요해서 작은 n에서는 느리고, brute는 준비 없이 바로 비교하지만 n²로 늘어서 n이 커지면 LSH가 앞선다.

이차 확인은 맞았다. 비교 횟수는 n이 두 배일 때 정확히 4.00배(499,500 → 1,999,000)였고, 시간도 3.86~4.13배로 4배 근처에서 흔들렸다.

n=8,000에서 brute가 111초 걸려 시간이 먼저 불편해졌다. 메모리는 LSH가 17.8 MB로 16 GB의 약 0.1%라 문제가 아니었다. n=16,000은 측정하지 않았고, 이차로 추정하면 brute가 약 440초다.

## Task 3 — 비교 횟수 줄이기

hash 128개를 band 32개(band당 r=4)로 나눴다. S-curve의 step은 (1/32)^(1/4) ≈ 0.42로 임계값 0.6보다 아래다. 이러면 s=0.6인 쌍이 후보가 될 확률이 1-(1-0.6^4)^32 ≈ 98.8%라 놓치지 않는다. 대신 덜 비슷한 쌍(s=0.4에서 56%)도 후보로 뽑혀 비교가 늘어나는 게 대가다.

step을 올려 봤다. b=16(r=8, step 0.71)은 비교 90회에 recall 74.4%, b=8(r=16, step 0.88)은 비교 11회에 recall 9.1%였다(b=32는 125회, recall 100%). step을 올릴수록 비교는 줄지만 진짜 비슷한 쌍을 급격히 놓친다.

하네스가 hash 비용을 안 매기는 게 공정하지 않은 구간이 있다. Task 2에서 교차점(n=800~900) 이전에는 brute가 LSH보다 더 빨랐는데, 이때는 signature를 만드는 hash 오버헤드가 비교 비용보다 크기 때문이다.
